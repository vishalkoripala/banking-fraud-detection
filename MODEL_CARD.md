# Model Card — Banking Fraud Detection

## Model details

| | |
|---|---|
| Model type | Selected automatically between L2-regularized Logistic Regression and HistGradientBoosting, based on which wins 5-fold stratified CV PR-AUC on the training split |
| Currently deployed | `logistic_regression` (see `model/model_metadata.json` for the live artifact's details — this can change if the pipeline is retrained) |
| Framework | scikit-learn 1.8 (pipeline), SHAP 0.52 (explanations), FastAPI (serving) |
| Inputs | `Time`, `V1`–`V28` (PCA-anonymized transaction features), `Amount` |
| Output | Fraud probability in [0, 1], plus a flag/no-flag decision at a tuned threshold |
| Training script | `train_final_model.py` |

## Intended use

**In scope:** a real-time or batch scoring component in a larger fraud
review workflow — surfacing a probability and a ranked list of contributing
factors that a rules engine or human analyst uses to decide whether to hold,
review, or approve a transaction.

**Out of scope:**
- **Automated, unreviewed denial of transactions.** This model has a
  ~17–21% false-negative rate and a nonzero false-positive rate at its
  tuned threshold (see Evaluation). It's built to prioritize cases for
  review, not to be the sole and final word on a customer's transaction.
- **Any dataset with a different feature schema.** `V1`–`V28` are PCA
  components fitted by the original dataset's creators on their specific
  transaction data. They are not portable to a different processor's raw
  features — this model would need to be retrained on that processor's
  own data, with its own PCA (or other) transformation.
- **Deployment without ongoing monitoring.** See Limitations.

## Training data

ULB Machine Learning Group's "Credit Card Fraud Detection" dataset (Kaggle:
`mlg-ulb/creditcardfraud`; originally described in Dal Pozzolo et al.):
284,807 European cardholder transactions over 48 hours in September 2013,
492 confirmed fraud (0.173%). Features `V1`-`V28` are the output of a PCA
transformation applied by the original researchers for confidentiality;
`Time` and `Amount` are the only features left in original units.

This is a widely-used academic benchmark, not a live production feed. See
Limitations for what that means for deployment.

## Evaluation methodology

A single stratified 80/20 train/test split is held fixed
(`random_state=42`). Model choice and decision threshold are both selected
using only 5-fold cross-validation **within the 80% training split** — the
20% test split is never touched by any tuning decision. The winning
pipeline is fit once on the full training split, then scored **exactly
once** on the untouched test split. Those test-split numbers, not the CV
numbers, are what's recorded in `model/model_metadata.json` and below,
because they're the only numbers produced by a model evaluated on data it
never influenced in any way.

### Held-out test performance (56,962 transactions, 98 confirmed fraud)

| Metric | Value |
|---|---|
| PR-AUC (Average Precision) | 0.708 |
| ROC-AUC | 0.971 |
| Precision @ deployed threshold | 0.832 |
| Recall @ deployed threshold | 0.806 |
| F1 @ deployed threshold | 0.819 |

At the deployed threshold, out of 98 real fraud cases in the test set, 79
were caught and 19 were missed; 16 legitimate transactions were flagged
incorrectly. Full confusion matrix in `model/model_metadata.json`.

**Note on ROC-AUC vs. PR-AUC:** ROC-AUC alone would suggest this problem is
close to solved (0.97). PR-AUC (0.71) is the more honest number for a
0.17%-prevalence problem — see the main README for why.

## Explainability

Every prediction from `POST /predict` includes the top 5 features driving
that specific score, via exact Shapley values (`shap.LinearExplainer` for
the currently-deployed logistic regression; the code also supports
`shap.TreeExplainer` if a tree-based model is selected on a future
retrain — see `explain.py`). Values are reported in the model's original
input units (e.g. "V14 = -6.17"), not scaled/capped units, paired with the
SHAP contribution and a direction (`increases_risk` / `decreases_risk`).

Global feature importance (which features matter most across many
predictions, not just one) is in `outputs/global_feature_importance.png`,
generated by `generate_explainability_report.py`. The top drivers — `V4`,
`V10`, `V14`, `V12`, `V17` — line up with patterns independently reported
in public analyses of this same dataset, which is a reasonable sanity check
that the model has learned genuine structure rather than noise.

**Caveat specific to this dataset:** because `V1`-`V28` are anonymized PCA
components, "V14 is the top driver" is not further explainable in business
terms (it doesn't map back to "unusual merchant category" or similar) — that
mapping was deliberately destroyed for confidentiality when the dataset was
built. In a deployment on raw (non-anonymized) features, the same SHAP
approach would produce directly business-interpretable factors.

## Limitations

- **Temporal validity.** All data is from a single 48-hour window in 2013.
  Fraud patterns shift over time (new attack patterns, changed spending
  norms); a score this good on 2013 data is not a guarantee of equivalent
  performance on next month's live traffic. Treat this as a template
  pipeline to retrain on recent, representative data before relying on it.
- **Geographic/demographic scope.** European cardholders only, over a
  short window. No claim is made about performance on other populations,
  merchant categories, or transaction types (e.g. card-not-present vs.
  in-person) not represented in this sample.
- **Fairness is not assessable here.** Because `V1`-`V28` are anonymized
  and no demographic fields are present, standard fairness audits
  (disparate impact by protected class, etc.) cannot be performed on this
  dataset. That doesn't mean the underlying live system is fair — it means
  this particular dataset can't tell you either way, and a live deployment
  needs its own fairness evaluation on its own data.
- **Class imbalance handling (`class_weight="balanced"`) skews raw
  probabilities** away from the true prior (see main README). Anything
  consuming this model's output must use the tuned threshold in
  `model_metadata.json`, not an assumed 0.5 cutoff.

## Threshold governance

The deployed threshold (`model/model_metadata.json` →
`decision_threshold`) was chosen to maximize F1 on training-split CV — a
symmetric objective that weighs a missed fraud and a false decline equally.
Real institutions rarely weigh these equally (a missed $5,000 fraud and an
annoyed customer on a $40 decline are not the same cost), so this threshold
should be treated as a reasonable engineering default, not a business
decision. Moving it is a product/risk decision and should involve whoever
owns fraud-loss budget and customer-friction budget, not just be changed in
code by an engineer. `outputs/pr_curve_comparison.png` is the right tool
for that conversation — it shows the actual precision/recall trade-off at
every threshold, not just the one currently deployed.

## Monitoring & retraining recommendations

- **Track live precision/recall against confirmed fraud labels** (from
  chargebacks/investigations) on a rolling window, not just at
  deployment time — both data drift (spending pattern shifts) and concept
  drift (new fraud tactics) will erode performance silently otherwise.
- **Watch the score distribution itself**, not just accuracy metrics — a
  sudden shift in the distribution of `fraud_probability` across live
  traffic (even before enough labels come back to compute precision/recall)
  is often the earliest warning sign of drift.
- **Re-run `train_final_model.py` on a recent, representative window on a
  regular cadence** (frequency depends on how fast fraud patterns move in
  your environment) rather than treating this as a train-once artifact.
- **Log every prediction** (already wired into `api.py` →
  `logs/predictions.log`) to support both drift monitoring and after-the-fact
  audits of specific decisions.
